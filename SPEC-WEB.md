# Advanced Schedule Part 2 — Web Interface Specification

## Context

Part 1 (SPEC.md, M1–M5 done, M6 polish pending) produced a deterministic MC-free timetable simulator with conflict detection, a deterministic collapsed rail-graph model with real curve geometry, and in-game presentation. Part 2 exposes the network and the simulator through a **web interface served by an HTTP server embedded in the Minecraft server JVM**:

1. **Live view** — 2D map of all rail networks with live trains; time-distance diagrams between any two stations (actual observed movements overlaid with the simulated plan); notifications for live issues (deadlocks, extreme signal waits, extreme detours).
2. **Timetable planner** — preset schedule library (imported from live trains or uploaded from advanced-schedule items); drag-and-drop virtual assignment of presets to trains; deterministic simulation with map playback, corridor diagrams, conflict/root-cause lists; condition value tweaks from the browser; **Deploy** applies assignments to real trains.

Full architecture, API tables, and rationale: `plans/hereisadraftdriftingmccarthy.md` (authoritative for implementation detail). This spec records durable decisions, constraints, and milestone status.

## 1. Decisions record (interview 2026-08-03)

| Topic | Decision |

| Hosting | Embedded HTTP server in the MC server JVM; HTTPS via optional reverse proxy (documented) |

| Alerts | Web notification panel only (no Discord webhook this phase) |
| Mod split | `net.Realism.web` bounded package; the actual migration is a later, separate effort |

## 2. Hard constraints (must-not-violate)

1. **Zero new runtime dependencies.** JDK `com.sun.net.httpserver.HttpServer` + SSE (no WebSocket), MC-bundled GSON, JDK `java.net.http.HttpClient` for Discord. Shading is the documented fallback, not the default.
2. **`net.Realism.web` is server-only.** It never references client classes or MC packet classes (dedicated-server class-verification rule). Core→web coupling is exactly two bootstrap lines: `WebBootstrap.init()` in `RealismMod.commonSetup()` and `WebCommands.register(...)` in `RealismCommands`.
3. **Secrets never live in ForgeConfigSpec.** COMMON tomls ship in client installs; SERVER-type configs sync to clients. Secrets + allowlist live in server-only `config/realism-web/*.json`.
4. **Graph node/edge ids are per-version transients.** Every payload that mentions them carries `graphVersion`; only `trackGraphId`/`stationId`/`crossingId` UUIDs may be persisted or used across versions. History clears on rebuild; corridors 409 on version mismatch.
5. **Web sims are deterministic**: `maxWallMillis = 0` by default; a nonzero safety cap must mark `SimResult.truncated` and surface it.
6. **Server-thread discipline.** Only LiveTrainSampler, tick-side analyzers, WebGraphStore.rebuild, DeployService, PresetStore train-import, and `HeadlessSimService.prepare` may touch `Create.RAILWAYS`/`Level` — all on the server thread; everything else runs on web worker threads over immutable snapshots.
7. **Deploy ordering** (verified against Create 6.0.8 + `ScheduleRuntimeMixin`): strip `Progress` from the tag → `runtime.discardSchedule()` → guard non-empty → `runtime.setSchedule(s, false)` → `setAdvancedSchedule(true)` **after** (the mixin resets the flag at `setSchedule` TAIL).
8. **`RNetworking` wire ids are positional** — preset packets append at the end; `VERSION` bumps `"8"→"9"` when they land (W4).
9. **SSE is exempt from the CSRF custom header** (EventSource cannot send one) — cookie + Origin check only; all other mutations require `X-Realism-Csrf`.
10. **Never reuse `RailGraphCache` for web** (10 s TTL would re-translate huge graphs on poll cadence). `WebGraphStore` rebuilds only on checksum change or max-age, floored by a min-interval.

## 3. Design summary

- **Threads**: HTTP pool "Realism-Web-N" (4); per-SSE-client writer threads with bounded queues (drop-oldest, stall disconnect); "Realism-Web-Analyzer" (graph JSON/gzip, detours, corridors); "Realism-WebSim" (headless engine runs — separate from the in-game item sim worker); "Realism-Web-IO" (preset/audit writes). Server-thread work is marshalled via `server.execute` + future.
- **Graph**: `WebGraphStore` per TrackGraph `{RailGraph, SimTopology, SimGraph, gzJson, version, checksum}`; JSON includes `RailEdge.shape` polylines, coords quantized to 0.1-block ints; ETag = version.
- **Live**: sampler every `WebLiveSampleTicks` via `SimTopology.locate`; volatile latest frame + per-train history rings (`WebHistorySampleSeconds` × `WebHistoryHours`); single multiplexed SSE stream `/api/events` (`hello/trains/trainMeta/graph/graphIndex/notify/sim/deployed/reset` + heartbeat).
- **Analyzers**: SIGNAL_WAIT from Create's `Navigation.ticksWaitingForSignal`; DEADLOCK via Tarjan SCC over the wait-for graph from signal-group occupancy/reservations (incl. `intersectingResolved` crossings), confirmed over a window; DETOUR via `navigation.distanceToDestination` vs `SimPathfinder` shortest, off-thread.
- **Headless sim** (core `HeadlessSimService`): `prepare` (server thread) = NetworkSnapshotter + per-assignment `ScheduleCompiler` override (fresh progress; upgrades idle/obstacle trains); `run` anywhere. Results as `SimDebugExporter` JSON (+`rootCauses`, `meta.graphVersion`) in a byte-bounded LRU.
- **Corridors**: `SimDiagram.fromPath` (refactor: corridor decoupled from the phantom, `populateLines` extracted, projection helpers public); station groups via CRN tags else platform-number stripping; paths via `SimPathfinder` with no traffic penalties.
- **Presets** (core `PresetStore`): `<world>/realism/presets/<uuid>.json`, schedule as SNBT validated by the `AdvancedScheduleSavePacket` round-trip template; web edits restricted to the `ScheduleCompiler`-matching key whitelist; 3 C2S + 1 S2C packets for item upload/download.
- **Auth**: OAuth code flow; HMAC-signed identity cookie (tier re-resolved from the allowlist per request; synthetic sessions from one-time tokens carry a fixed tier); allowlist hot-reload; rate-limited `/auth/*`.
- **Frontend**: Svelte 5 runes for UI truth, plain mutables for the 60 fps path; two-canvas map (offscreen raster static layer + per-frame dynamic layer), Web Worker geometry pipeline (typed arrays, arc tables, Douglas-Peucker LOD tiers, uniform grid), sim_debug.html playback math ported with real curve geometry; exact `SimTimeFormat`/`TimeDistanceDiagramWindow` semantic ports for diagrams.

## 4. Config

`RealismConfig.Common` push-block **"Web Interface"** (non-secret; defaults chosen for safety): `Web Enabled` (false), `Web Bind Address` (127.0.0.1), `Web Port` (8455), `Web Public Url` (""), `Web Default Tier` ("none" = allowlist only; otherwise the tier a first-time Discord login is auto-enrolled at), `Web Http Threads` (4), `Web Max Sse Clients` (20), `Web Live Sample Ticks` (20), `Web History Sample Seconds` (5), `Web History Hours` (2), `Web Graph Node Cap` (100000), `Web Graph Min Rebuild Seconds` (60), `Web Graph Max Age Seconds` (300), `Web Signal Wait Alert Seconds` (120), `Web Deadlock Confirm Seconds` (30), `Web Detour Ratio` (1.75), `Web Detour Min Blocks` (500), `Web Sim Max Horizon Hours` (48), `Web Sim Max Queued` (4), `Web Sim Cooldown Seconds` (15), `Web Sim Wall Cap Seconds` (0 = deterministic), `Web Sim Cache MB` (128), `Web Projection Stale Seconds` (300), `Web Session Hours` (72), `Web Preset Max Count` (500), `Web Plan Max Count` (200),  `Web Replay Kept` (20, 0=off), `Web Replay Buffer Seconds` (300), `Web Replay Lead Seconds` (120), `Web Replay Tail Seconds` (60), `Web Replay Radius` (1200), `Web Dev Login` (false, temporary).

Server-only files under `config/realism-web/`: `secrets.json` (discordClientId/Secret, auto-generated sessionSecret; 600 perms attempted), `allowlist.json` (`{"users":{"<discordId>":{"tier":"none|viewer|planner|deployer","note":"..."}}}`), both hot-reloadable (`/realism web reload` or 30 s mtime poll). With `Web Default Tier` set, an unknown Discord id is written into `allowlist.json` at that tier on its first login (note `"<name> (first login)"`); an id that already has an entry is never re-enrolled, so a `none` entry is a permanent block.

Commands (op 3): `/realism web status | reload | refresh [graph] | allow <discordId> <tier|none> | deny <discordId> | list | session <tier>`.

Every 5-min re-prepare rerolls the dice, hence curves changing between reruns. Evidence-based: never speeds up trains that were never seen fast. Known gaps: the first projections after a server restart have no observation history yet; the in-game item-based sim (`SimulationService`) still snapshots without floors and can under-speed the same way; powered *acceleration* is not restored (secondary effect). **Correction (user: powered and unfueled config stats are identical on the field server):** the real mechanism was Tramways after all, from the other side — its `TrainMixin` shadows and continuously rewrites `train.throttle` to enforce sign zones (never touching `maxSpeed()`), and the measured 131/244 = 0.537 is a throttle fraction (≈130 zone / ≈245 config top). The "trust live throttle when the schedule has THROTTLE instructions" heuristic was therefore still poisoned — those schedules DO have throttle instructions, and the live value at snapshot was the zone's, not the schedule's. Snapshot now NEVER reads `train.throttle`: it reconstructs the schedule-intended throttle as the last THROTTLE instruction executed before the current entry (walking backwards, wrapping when cyclic, 1.0 when the schedule never sets one) — Tramways zones stay modeled by per-edge sign caps. The observed-speed floor stays as a safety net for genuinely fuel-split servers. **Fourth round — "sim over-estimates acceleration":** instrumented plan payloads (`acc`/`top`/`thr` per line) proved the snapshot captures the correct Realism-reduced acceleration (mixin-honored, 0.0043–0.005) and the engine integrates it exactly (plan standstill→800-block time matched √(2d/a) theory to the tick) — yet real departures measured 40–70 % slower than plan. Root cause: the translator applied a Tramways speed sign only to the track segment containing it, but Tramways signs set a PERSISTENT per-train limit lasting until another sign supersedes or a temporary-end sign releases it — real trains crawl through whole zones (station throats), sim trains bounced back to line speed one segment later, reading as over-acceleration. Fix: `TramwaysCompat.getSignZoneKmh` classifies signs (speed = zone start, temporary-end = release, whistle/arrow = ignored so they can't clear a zone) and `RailGraphTranslator.directionalSignCap` propagates the entering zone across every span until superseded (per track run — zones crossing junctions can't be tracked statically; per-edge cap = min zone active over the edge, conservative). Graph JSON stays shape-compatible (release signs are excluded from the sign display list). **Fifth round — zones through junctions (per-train sign state):** static per-walk propagation could never carry a zone across a junction (the correct limit there depends on the route the train arrived by — unrepresentable as track data) and silently over-capped trains that entered a walk mid-zone without passing its sign. Reading Tramways' sources settled the true mechanic: signs RUN ON the train and rewrite `Train.throttle` itself when the front crosses (permanent `SpeedSignDemand` sets it; `TemporarySpeedSignDemand` — which *extends* SpeedSignDemand, instanceof order matters — stashes the old value in `tramways$storedPermanent` and sets it; `TemporaryEndSignDemand` restores the stash; all clamped by per-train `tramways$primaryLimit`; no anticipatory braking — demands apply at distance 0). The sim now mirrors that exactly: `TramwaysCompat.getSignEvents` extracts `{temporary, release, permanent}` throttle fractions per sign direction (+ `getPrimaryLimit`/`getStoredPermanent` per-train readers — ITram cast / cached reflection); the translator emits `SimEdge.SignEvent`s (offset-sorted, Tramways tick order at equal offsets) through a new `SimTopology` side table; `SimEngine.advance` fires events the head crosses `(from, to]` and `applySignEvent` reproduces `TrainMixin.tramways$tickSigns` on `TrainState.throttle`/`storedPermanent` — so zones ride the train through junctions until superseded or released, and the static `SimEdge.signCap` (kept for display) plus the old lookahead-braking helper are no longer engine inputs. Because live `train.throttle` IS the zone state and the engine now replays sign crossings + schedule THROTTLE instructions forward, `NetworkSnapshotter` reverted to seeding the live throttle (clamped) plus `primaryLimit`/`initialStoredPermanent` — the schedule-reconstruction workaround (fourth-round fix) is deleted; a train snapshotted mid-zone starts slow and recovers exactly at its release sign. 4 new JUnit cases (`SignZoneTest`): zone persists through a real junction node, temporary zone ends at its release sign, seeded stored-permanent restored by release, primary-limit clamp. **Field verification (same day):** spatial speed profiles (median km/h per 200-block corridor bin, per direction) showed plan matching actual's *shape* but running 1.5–2× hot, one sim train at the full 299 km/h config top — while real trains plateau at ~164 ≈ 0.55 × 299 under long propagated 100%-sign zones. Cause: Tramways' `SetPrimaryLimitInstruction` is how servers set line speed FROM THE SCHEDULE (sets throttle via its ChangeThrottleInstruction super AND arms `tramways$primaryLimit`); the compiler had mapped it to a plain THROTTLE entry ("close enough" under the static model), so sim trains crossing a 100% sign event sprang back to full speed where real ones re-clamp to line speed. Fix: `InstructionKind.PRIMARY_LIMIT` — the engine sets `TrainState.primaryLimit` (now mutable, seeded from the spec) + throttle; sign events clamp against the live value; plan JSON gains a `plim` debug field to verify the ITram seed reads on the field server. +1 JUnit case (100% sign cannot escape an armed primary limit). **Second verification round:** `plim` seeds read correctly (0.5/0.53/0.67/0.76 regional stock, genuine 1.0 for Eurostar/TGV); departure ramps now MATCH (Eurostar 1: actual 618 vs plan 649 ticks — 5%); but per-train mid-corridor profiles showed plim=1.0 trains cruising 264–298 km/h in plan vs a real ~164 plateau with 180–211 peaks only on the corridor's single 335-block straight (211 = exact 164→v recovery at realism accel — a *turn-speed* signature, not throttle). Cross-checked Create's `Navigation` sources: the curve listener slows to `maxTurnSpeed` for EVERY bezier edge — gentle curves of any radius, steep straight climbs, and flat straight bezier connections included; the only exemption is straight-in-XZ (axes antiparallel < 1/64) + elevated (ΔY > 1/16) + mild grade (< 0.225). The translator only produced turn ranges where XZ curvature was tight (`speedForRadius` 0 above radius 5000, Y ignored) — so on a bezier-built mainline sim trains sprinted where real ones bounce off turn speed continuously.
